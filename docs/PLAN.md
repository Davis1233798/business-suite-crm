# 六套商業系統與 Portfolio：規格及驗收計畫

規畫日期：2026-10-30。狀態：規畫完成，實作尚未啟動。電傷暫解讀為電商。產品名稱均為暫名，個人姓名、經歷、客戶與成果不得虛構。

## 1. 交付邊界

建立六套可獨立操作、具後端持久化資料的系統與一個 Portfolio。第一階段為可展示且通過業務驗收的版本，第二階段才接正式金流、電子發票、簡訊、郵件與設備。不得把只有靜態畫面、localStorage 或假成功訊息當成完整系統。

Portfolio `/`，MES `/mes`，ERP `/erp`，POS `/pos`，CRM `/crm`，餐飲 `/dining`，電商 `/shop`（管理 `/commerce`）。各系統具有獨立首頁、導覽、角色、資料範圍、操作說明及返回 Portfolio 連結。先採單一部署內的獨立領域模組，後續可拆為子網域，避免第一版就承擔微服務維運成本。

展示版：繁體中文、TWD、Asia/Taipei，資料庫時間存 UTC；桌面及手機。現金、模擬付款及模擬發票清楚標示。正式財稅、薪資、跨境稅務、信用卡卡號保存、硬體控制不在第一版範圍。

## 3. 共用架構與約束

建議 TypeScript、React、Vinext、Cloudflare Workers 與 D1，使用 Sites 支援的 starter；單一入口與同源 API。採 SQL migration、外鍵、交易及條件更新。以 repository 介面隔離資料庫；若日後高寫入量需求超過已測能力，再評估資料庫遷移。開發先驗證 D1 交易與併發機制，不假設 Node 原生套件均可在 Workers 執行。

領域資料各自擁有：MES 管製造；ERP 管採購、正式庫存與財務；POS 管門市交易；CRM 管商機；餐飲管餐桌與出餐；電商管網路通路。第一版各自使用隔離種子資料。第二階段以明確版本的事件整合，不能讓多套模組直接寫同一張庫存表。

共用表：organizations、users、memberships、roles、permissions、audit_events、idempotency_keys、outbox_events。每個領域表帶 organization_id。不可單靠前端隱藏按鈕控制權限。API 統一回傳資料或可辨識錯誤碼、request_id，清單有分頁與篩選。

共用模組驗收：

| ID | 模組 | 驗收方法與通過條件 |
|---|---|---|
| C01 | 身分與角色 | 管理員、操作員、唯讀三種帳號逐一呼叫讀寫 API；越權回 403，未登入 401；登出後工作階段失效 |
| C02 | 組織隔離 | A 組織帳號猜測 B 記錄 ID，查詢、修改、匯出均無法取得 B 資料 |
| C03 | 稽核 | 修改金額、角色、庫存及退款，記錄 actor、時間、前後值、原因、request_id；一般帳號不可改稽核 |
| C04 | 輸入與匯入 | 空值、負數、超長字串、重複鍵、錯誤 CSV 欄位均有明確錯誤；匯入先預覽，錯誤列可下載，無半筆資料 |
| C05 | 持久化與備份 | 建立資料後重啟仍存在；在獨立環境還原備份，核對筆數與帳務/庫存合計 |
| C06 | 併發與重試 | 同一 idempotency key 重送 3 次只有一筆交易；不同 key 搶最後一件庫存只有一方成功；失敗完整回滾 |
| C07 | UX 與無障礙 | 375、768、1440px 無非預期橫向捲動；鍵盤可操作、表單有 label、焦點可見；有 loading、空資料、錯誤與重試狀態 |
| C08 | 匯出與報表 | 篩選後畫面、API 與 CSV 合計相等；CSV 公式型內容安全跳脫；時間跨日依台北時區一致 |
| C09 | 部署與監控 | 全新環境依 README 完成 migration、seed、啟動；健康檢查成功；錯誤含 request_id，日誌無密碼或 token |

金額以整數最小貨幣單位存放，禁止浮點帳務；數量可採固定精度。金額計算順序：行金額→行折扣→訂單折扣分攤→稅→運費/服務費；四捨五入規則以 golden fixtures 固定。貨品不得負庫存；更正用反向分錄，不刪除已過帳歷史。所有狀態轉移在服務端驗證。

## 11. 跨系統整合（第二階段）

CRM成交→ERP銷售單；ERP生產需求→MES工單；MES完工→ERP成品入庫；POS/電商銷售→ERP扣庫及應收；餐飲付款→ERP營收。事件包含event_id、schema_version、organization_id、source_id與occurred_at；採outbox、重試及去重，失敗有可查狀態與人工補送。

驗收：同event重送3次只生一張目的單；目的服務停用後恢復可補送；來源與目的金額/數量一致；跨組織事件拒絕。未完成此驗收前，Portfolio不得宣稱六系統即時整合。

## 12. 實作順序與交付關卡

1. P0：專案骨架、資料模型、金額工具、權限、migration、隔離seed、Portfolio路由；通過C01-C07核心檢查。
2. P1：ERP庫存/單據骨架及POS完整交易，先驗證金額、庫存與退款共用規則。
3. P2：CRM與電商，完成商機及線上訂單主流程。
4. P3：餐飲與MES，完成桌次/出餐與工單/報工/追溯。
5. P4：各系統剩餘模組、報表、案例頁、備份還原、部署與全套驗收。
6. P5：選用的跨系統整合與正式外部服務，另立供應商sandbox驗收。

每關交付可啟動程式、migration、seed、API規格、測試與結果，不以截圖代替後端驗收。不預先承諾工期；第一個完整垂直流程完成後依實際速度估算。
